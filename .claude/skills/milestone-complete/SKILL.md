# マイルストーンの完了を判定する

**「テストが緑だから完了」ではない。** 完了条件は `docs/roadmap.md` に
マイルストーンごとに明記されており、1 項目ずつ実測で照合する。

このプロジェクトは人が見ていないループでエージェントが実装する。だから完了
判定の質がそのまま次のマイルストーンの土台になる。M0 では実際に、コードは
すべて緑なのに `CLAUDE.md` が「ビルドシステムは存在しない、コマンドを実行
するな」と書いたまま残り、最終レビューで **Critical** として検出された。
放置していれば M1 のエージェントは M0 の成果物を無視してビルド系を再発明していた。

## 手順

### 1. 完了条件を読む

`docs/roadmap.md` の該当マイルストーンの節を開き、**目的 / ゴール / 完了条件 /
非ゴール** を確認する。完了条件を箇条書きで書き出し、これから 1 つずつ埋める。

**非ゴールも読む。** 完了条件に無いものを作っていたなら、それはスコープ超過で
あって完了の材料ではない。

### 2. 各条件を実測で照合する

条件ごとに「どのコマンドを叩き、何が返ったか」を記録する。

**「通った」と書くのは証拠ではない。実際の出力を貼る。** M0 ではこの区別が
曖昧だったために fix round を 2 回消費した。「C4819 は消えた」という記述だけが
あり、コンパイラ出力が無かった。

条件が挙動に関するものなら、その挙動を再現して見せる。たとえば「クラッシュが
有限時間で赤くなる」なら、実際に赤くなるまでの秒数を出力ごと記録する。

**終了コードを見る。出力の PASS 行を数えない。** M1 では `test-tools-slow` を
「27 PASS 緑」と報告した直後に、その実行が exit 1 だったことが分かった。失敗した
実行にも PASS 行は出る。パイプを通すと `$?` はパイプ最後のコマンドの値になるので、
`| tail -3` を付けたまま `echo $?` すると `tail` の終了コードを読むことになる。

```
cmd > /tmp/out.txt 2>&1; echo $?    # cmd の終了コード
cmd | tail -3; echo $?              # tail の終了コード（間違い）
```

**「テストが存在する」を「検証されている」と読み替えない。** 完了条件が
「〜をテストする」と書いているなら、そのテストが `tools/dev.ps1` か
`.github/workflows/` から実際に呼ばれていることを `grep` で確かめる。M1 では
517 行のテスト群がどのレーンからも走っておらず、手で叩けば緑になることを根拠に
「満たす」と判定してしまった。人が思い出したときだけ走るものは、
「CI が唯一の正本の検証結果」という自分たちの規則の下では検証機構ではない。

検査そのものを足したり変えたりしたなら `prove-a-check-works` skill を使う。
壊して落ちることを確認していない検査は、通っても証拠にならない。

### 3. 全レーンを回す

```
pwsh tools/dev.ps1 test             # tools の速いテスト + L1 + L3
pwsh tools/dev.ps1 test-asan        # L2
pwsh tools/dev.ps1 test-tools-slow  # CI 専用。ローカルで叩くと数分かかる
```

`test` は fail-fast で、L1 が落ちると L3 は走らない。両方の結果が要るなら
落ちた側を直してから回し直す。所要時間は `CLAUDE.md` の表を見る（実測値を
書いてあるので、乖離していたらそちらも直す対象である）。

**`test-tools-slow` をローカルで叩くと環境が壊れることがある。** 中の
`OpenCvRestore.Tests.ps1` は自己修復を検証するために OpenCV ツリーを意図的に
破壊して取り直す。構成ハッシュを変えた直後で、その成果物が CI にまだ無いと、
取り直しに失敗してツリーが消える。CI がビルドを終えてから `opencv.ps1 restore`
すれば戻る。

**Unity に関わる完了条件があるなら、そのレーンも回す。** L1 / L3 が緑でも Unity 側は
何も確かめていない。

```
pwsh tools/dev.ps1 test-unity-editmode   # L4
pwsh tools/dev.ps1 test-unity-player     # L5
pwsh tools/dev.ps1 test-unity-tarball    # tarball からの導入
```

**`test-unity-tarball` は既定では 1 platform 分しか確かめない。** 全部入りを検査する
には `-PluginSource` で他 platform の plugin 木を渡す必要がある。渡さなければ従来
どおり 1 platform で走って緑になる —— **全部入りのふりはしないが、引数が抜けていた
ことも出力からは分からない。** 完了条件が全部入りについて言っているなら、**実行した
コマンドラインをそのまま報告に貼る。**「レーンを回した」と「そのレーンが完了条件を
見た」は別である。

### 4. ドキュメントの陳腐化を確認する ★ここが最も抜ける

コードが正しくても、文書が古いと次のセッションを誤誘導する。以下を実際に開いて
現状と突き合わせる。

**`CLAUDE.md`** — 最重要。**毎セッション自動で読み込まれる**ため、古いと以降の
全エージェントに効き続ける。次を確認する:

- 「リポジトリの現状」がいま存在するものを説明しているか
- 開発コマンドの表が `tools/dev.ps1` の実際のサブコマンドと一致するか
- 記載の所要時間が実測と乖離していないか
- ファイル配置の表に、追加・削除されたディレクトリが反映されているか
- 「マイルストーン（現在地: ...）」が正しいか
- 逆方向の誇張が無いか（まだ無い機能を「ある」と書いていないか）

**`README.md`** — status callout が現状と一致するか。対応プラットフォームや
OpenCV 統合の有無を過大に書いていないか。

**`docs/roadmap.md`** — 現在地の記述と、次マイルストーンの前提条件。

**`docs/README.md`** — 文書一覧に新しい文書が載っているか。

**`docs/api-reference.md`** — 公開している C ABI と C# API の一覧。**関数を足したなら、
冒頭の対象範囲（「M2 で公開した C ABI の N 関数」のような数え）と、末尾の「まだ無い
機能」の一覧が同時に古くなる。** 足した機能が「まだ無い」側に残っていないか必ず見る。

**`docs/abi-ownership-and-versioning.md`** — 所有権契約（§1）と API allowlist（§3）の
正本。**新しい所有権の形や新しいモジュールの関数を足したなら、ここが最初に古くなる。**
allowlist に載っていない関数を出荷している状態は、正本が正本でなくなっているという
ことである。

**数えている数を全部洗う。** 「公開 ABI は N 本」「allowlist は N 本」「Release の
asset は N 件」「EditMode は N 件」のような数はリポジトリ中に散らばっていて**一斉に
古くなる。** `grep -rn` で数字ごと探し、増減分を全部直す。

**そのマイルストーンが「これまでの記述は誤りだった」と暴いたものは、訂正として明記
する。** 黙って直すと、同じ誤解が別の文書に残っているかを誰も確かめられない。M3.5 が
これだった —— 複数の文書が `imgcodecs` を「リンク済み」と書いていたが、
`cmake/FindOpenCvUnityDeps.cmake` の `COMPONENTS` には無く、リンカが `cv::imencode` /
`cv::imdecode` を未解決にして初めて分かった。

### platform を足したなら、その一覧を全部数え直す

**M4 で数を間違えた。** roadmap は「2 か所」と書いていたが実際は 3 か所で、
さらに数え直すと **17 箇所**あった（`add-a-platform` skill に一覧がある）。

判定の側でやることは 1 つ: **文書に書かれた数を信用せず、`git grep -c` で
数え直す。** 「公開 ABI は N 本」「asset は N 件」「EditMode は N 件」も同じで、
**これらはリポジトリ中に散らばっていて一斉に古くなる。**

### 「対象」と「実行環境」が一致しない条件を見分ける

M0〜M3.5 の完了条件はすべて「実行中の OS で確かめる」形だった。M4 で初めて
**クロスコンパイル**が入り、次の 2 つが別物になった:

- **ビルドできること** —— CI で確かめられる
- **動くこと** —— 実機が要る

**この 2 つを 1 行の完了条件に混ぜない。** 混ざっていると、ビルドが通った
時点で「満たした」と書きたくなる —— それは v0.1.0 が踏んだ
「ビルドできた ≠ 動く」そのものである。

M4 では 8 件のうち **2 件が実機を要求**しており、**CI では原理的に閉じない。**
そういう条件は判定表で「閉じていない」と書き、**人が実行する手順書**
（`docs/m4-device-verification.md`）に落とす。**「満たすが未実証」ですらない** ——
未実証は「検査は書いたが走る場所が無い」であって、こちらは「検査そのものを
CI で書けない」である。


### 5. 未処理の指摘を棚卸しする

実装中に「後で」と判断した項目を集め、それぞれ「このマイルストーンで直すか、
次に送るか」を明示的に決める。送る場合は次マイルストーンの計画か
`docs/roadmap.md` に書き、**理由と、間違っていた場合のコスト**を残す。

黙って消えた指摘は、次に誰かが同じ問題を踏むまで見えない。

### 6. AI レビューを済ませてから PR を出す

**このリポジトリでは人間のレビューを挟まない。PR を出す前の AI レビューが
唯一のゲートである**（`CLAUDE.md` の「変更を main へ入れるまで」）。

ブランチ全体の差分をレビューし、指摘が出たら直し、修正差分をスコープを絞って
再レビューしてから PR を出す。PR は「レビューしてもらう場」ではなく
「CI に判定させる場」である。

**再レビューを省略しない。** M1 では、レビュー指摘を潰した修正の波それ自体が
新しい欠陥を 3 つ作った。うち 1 つは「閉じた」と報告された完了条件が実際には
閉じていないもので、もう 1 つは、その波が閉じたばかりの欠陥型の再発だった。
修正は小さいのでスコープを絞った再レビューは安く、見つかるものは大きい。

**報告に書く SHA は、書く前に存在を確かめる。** 人のレビューが無いこの流れでは、
報告が実施内容の唯一の記録である。SHA は「履歴に在り、検査できる」という主張なので、
`git log -1 --format=%h` を叩いてから書く。台帳に転記する側も同じで、
確かめずに写せば同じ誤りを増やすことになる。

PR 本文には、ステップ 2 で集めた実測値と、ステップ 5 で次に送ると決めた項目を
理由つきで書く。**穴があるなら隠さず書く。**

### 7. CI で確定させる

```
gh pr checks <number> --watch --fail-fast
```

**CI が唯一の正本の検証結果である。** ローカルの緑は速さのための近似で、
merge 可否は CI が決める。ローカルで緑・CI で赤なら、CI が正しい。

全パスしたらマージする（squash のみ有効。本文にブランチの要約を書く）。

artifact が上がっていることも確認する。「upload ステップが設定されている」
ことと「実際に上がった」ことは別である。

**workflow に job を足したなら、必須チェックにするかを決めるまでが作業である**
（`CLAUDE.md` の「機構として強制されていること」）。PR に出るチェックを足しただけでは
merge は止まらない。**PR で起動しない workflow（tag や schedule が trigger のもの）は
そもそも必須にできない**ので、その場合は「必須にできない」と判定に書いて先へ進む。
決めずに通すと、「CI が見ている」を「赤ければ止まる」と読み違えたまま残る。

**「成功が N 件」で充足を判定しない。名前で突き合わせる。**

`gh pr checks` は `SUCCESS` 以外の状態も返す。M4 の PR では
`EditMode results` / `Standalone results` の 2 件が **`NEUTRAL`** だった ——
game-ci 自身が出す check run で、必須ではない。**成功件数を数えると
「20 / 22 だから未達」と読み違える。**

逆向きの読み違えのほうが危ない。**GitHub は必須チェックを
`successful` / `skipped` / `neutral` のいずれでも通す。** `skipped` で
通るということは、**条件で丸ごと飛ばした job は「緑」と同じ扱いになる**
—— `needs:` で前段に繋いだだけの job は、前段が落ちると skip され、
**止めるはずのチェックが止めない**（M4 で `if: ${{ !cancelled() }}` を
足して塞いだ）。

必須の一覧と実際の結果を、名前で突き合わせる:

```
gh api repos/<owner>/<repo>/branches/main/protection \
  --jq '.required_status_checks.contexts[]' | sort > req.txt
gh pr checks <n> --json name,state \
  --jq '.[]|select(.state=="SUCCESS")|.name' | sort > ok.txt
comm -23 req.txt ok.txt   # 空でなければ未達
```

**必須チェックの正本は GitHub 側の設定であって、`CLAUDE.md` の表ではない。**
増やしたなら表も直す（`README.md` の英語版も一緒に直す —— 二重に書いてある
のはその 1 箇所だけ、という状態を保つ）。


### 8. 判定を書く

完了条件を表にし、各行に「満たした / 満たしていない」と根拠を書く。
満たしていない条件があるなら、**満たしていないと書く。** 部分的な達成を
完了と呼ばない。

**「満たしたが、実証はしていない」を第 3 の欄として持つ。** 検査を足したものの、
現状では必ず通る側にしかならず、`prove-a-check-works` の手順で壊して落とせないものが
これに当たる。満たしたと書くのは正しいが、証拠の欄には「壊して確かめられるのはいつか」
を書く。**実証済みの条件と同じ見た目にしない** —— 見た目が同じだと、後から読む人は
どちらが検査でどちらが宣言かを区別できない。

## やってはいけないこと

- テストが緑であることを完了条件の代わりにする
- 完了条件を読まずに、作ったものを列挙して完了とする
- 文書の確認を飛ばす（M0 で Critical になった経路そのもの）
- CI を待たずに完了を宣言する
- 未処理の指摘を記録せずに落とす
