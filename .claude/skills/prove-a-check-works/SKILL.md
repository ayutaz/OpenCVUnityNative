# 検査が本当に検査していることを示す

**通ったことは、見ていることの証拠にならない。** 何も見ていない検査も通る。

M1 では、実装の各タスクが同じ欠陥を 1 つずつ生んだ。名前は違うが構造は同一である。

| タスク | 検査が見ていた形 | 外に落ちた隣の形 |
| --- | --- | --- |
| T1 | 区切り文字で join したハッシュ | 区切り文字を値に含む要素 |
| T2 | 終了コード | StrictMode の scalar 例外で「成功」した経路 |
| T3 | 拡張子と場所（denylist を allowlist と呼んでいた） | 想定外の名前・隠し属性・列挙されないファイル |
| T4 | 指定したコンパイラ | PATH から拾われた MinGW アセンブラ |
| T5 | 存在する manifest | 0 バイト・`[]`・`42`・空白だけの manifest |
| T7 | 送信した CMake flag | 上流の cmake が黙って上書きした結果 |
| F1 | `getBuildInformation()` の戻り値 | 本番が渡す cmake stdout（各行に `-- ` が付く） |
| F5 | 新しい license ファイルが増えたこと | 一覧に名前を足すだけで緑に戻せること |

**共通形: 著者が列挙した形は塞がれ、その隣が外に落ちる。** 列挙を長くしても閉じない。
次に足されるものは、その一覧に載っていない。

## 手順

### 1. 失敗を既定にする

「怪しいものを弾く」ではなく「積極的に認識されたものだけを通す」形にする。

分類できないものが `return $true` や `continue` に落ちる構造は、常に間違っている。
`verify-opencv-artifact.ps1` の冒頭にこの不変条件が書いてある:

> ツリーの下のどのファイルも、何かに積極的に認識されない限り
> 「問題無し」の判定に到達してはならない。

### 2. 本番が渡す入力で書く

**推測した入力に対して正しいテストは、検証しているように見えて何も見ていない。**

書く前に、本番の経路が実際に何を渡すか確かめる。関数を呼ぶ、ログを見る、実物を出力する。
形式が 2 通りあるなら両方を固定する。

F1 はこれを外した。抽出器のテストは `getBuildInformation()` の戻り値を使い、本番は
cmake の stdout を渡していた。内容は同じでも行頭が違い、本番だけが常に 0 件を返して
いた。テストは緑のままだった。

T7 も同じで、計画が推測した期待文字列（`FFMPEG: YES` の桁揃え）は実物に一度も現れず、
書いていれば永久に通る assertion になっていた。

### 3. 壊して、落ちることを見る

**これを飛ばしてよい検査は無い。**

検査対象をわざと壊し、検査が落ちることを確認してから戻す。

```
# 壊す（1 行変えるだけでよい）
pwsh -NoProfile -File <test>; echo $?   # 1 を期待
# 戻す
pwsh -NoProfile -File <test>; echo $?   # 0 を期待
```

両方の数字を実際に見るまで、その検査は「動く」と言えない。M1 では次がこれで見つかった:

- 回帰テストを集計ブロックの**後ろ**に書いていた。PASS 表示は出るが終了コードに
  影響せず、落ちないテストになっていた（hook `check-assertions-reachable.sh` が
  以後これを見る）
- 一覧と通知文書を突き合わせる検査が、実際に欠落を検出することの確認

**既にある緑のレーンを証拠として持ち出すなら、書く前に壊す。**

新しい検査を書くときだけの話ではない。「このレーンが緑だから完了条件を満たす」と
言おうとしているなら、**そのレーンがその欠陥に反応するかを先に測る。** 順序が逆で
あることに意味がある —— 後から測ると、既に緑であることが判断を汚す。

M3.5 の「全部入りの package で、Unity が自分の platform の binary だけを読み込む」で
実際にこれをやった。着手前に macOS の `.meta` を「Windows でも有効」に書き換えて
EditMode を回したところ、**10 passed のまま通った。** 当時の EditMode は `.meta` の
platform 設定を 1 つも読んでいなかったので、**そのレーンはその欠陥に対して構造的に
無感だった。** 壊さずに書いていれば「EditMode が緑なので満たす」と報告していた。
`.meta` を読む検査を足した今は、同じ壊し方で 16 件中 3 件が落ちる。

**その検査の答えが定数でないことを確かめる。**

検査が読む値が、壊れている場合も健全な場合も同じなら、その検査は何も見ていない。
**assertion の形が正しいことと、その述語が分岐することは別である。**

### 壊し方そのものを、書き残すときに確かめる

**「壊したら N 件落ちた」を記録するなら、記録した手順で本当に N 件落ちるかを見る。**

M3.5 の計画書は下書きの段階で「macOS の `.meta` に `Editor: OS: AnyOS` を書く」と
記録しており、その手順のまま「3 件落ちる」と書きかけた。**その手順では 2 件しか
落ちない。** 検査は `GetEditorData("OS")` を `"Windows"` と比較するので、`AnyOS`
では一致せず 1 件は通ってしまう。`OS: Windows` にすると 3 件落ちる。

**レビューが指摘して、マージ前に直した**（現在の計画書と文書はすべて
`OS: Windows` と「3 件」で揃っている）。危なかったのは、**数字のほうは正しく、
手順のほうだけが別の壊し方を指していた**点である —— 数字だけを見比べても
気づけない。

**壊し方を 1 文字変えると、検査の効き方が変わる。** 数字が合っていても、
書き残した手順が別の壊し方を指していれば、次に読む人が再現できない ——
再現できない手順は、検査を確かめたことの証拠にならない。

### 自分の機械の残留状態が、検査を緑にしていないか

**「ローカルで緑」は、ローカルにしか無いものに依存していることがある。**

M3.5 で `test-tools-slow` を「143 PASS、exit 0」と報告した直後、レビューが
**CI の Windows / macOS job では落ちる**ことを再現した。原因は、全部入りの
レーンを手で走らせた残骸として `Runtime/Plugins` に 3 platform 分の `.meta` が
残っていたことである。**clean checkout には 1 platform 分しか無い。**
`Runtime/Plugins` は git の追跡外なので、`git status` にも出ない。

必須チェック 2 本が赤になる状態を、**ローカルの緑が隠していた。**

- 検査が読むものが**リポジトリの追跡外**にあるなら、その中身は clean checkout で
  何になるかを確かめる
- テストが足りない要素を補うなら、**補う対象を数え落としていないか**を見る
  （M3.5 では binary は補ったが `.meta` を補っていなかった）
- 「N 以上」で書いた検査は、**N より多くあるべき場合に足りない状態を通す**。
  中身の一覧が契約なら `=` で数える

同じ M3.5 で、置き換えた**新しい**検査も 1 度これを踏んだ。Unity に `.meta` の解釈を
問う際、最初は `PluginImporter.GetCompatibleWithEditor()` を見た。**3 platform とも
`true` を返す**（このマシンで 2026-08-30 に実測）—— `.meta` は Editor を 3 つとも
有効にしたうえで、その下の `OS` の設定で振り分けているからである。見るべきは
`GetEditorData("OS")` だった。**壊して落ちるところを見たので気づいた。**

疑うべき述語の形: 常に `true` を返す能力照会、必ず存在するファイルの存在検査、
必ず 0 でない件数の `-gt 0`、そして**道具が無い環境で SKIP になる検査**。
**SKIP は「確かめていない」であって「合格」ではない。**

### 壊す前にコミットする

**`git checkout --` で戻すなら、壊す前の状態がコミットされていること。**

M4 で 2 回続けて踏んだ: 新しい配線を書いた直後、コミットせずに壊し方を試し、
戻すつもりの `git checkout -- <file>` が**未コミットの配線ごと巻き戻した。**
1 回目は tools のテスト、2 回目は 3 つの workflow への配線で、どちらも
書き直しになった。

**気づきにくいのは、検査自体は正しく赤くなる**ことである —— 壊した結果として
赤いのか、配線が消えた結果として赤いのかが、出力からは区別できない。

順序を固定する:

```
1. 実装して、検査が通ることを確かめる
2. **コミットする**
3. 壊す → 落ちることを見る → git checkout -- で戻す
4. （必要なら）検査を直して 1 に戻る
```

### 戻したことを確かめてからコミットする（上の対になる半分）

**壊す作業とコミットを混ぜない。**

2026-09-03 に踏んだ: 生成物（`native/include/ocvu/ocvu/*.h`）に検査用の行を
注入して落ちることを確かめたあと、**戻す前にコミットした。** 一緒に入ったのは
レビュアーが別のファイルへ当てた変異で、**どちらも `git add -u` が拾った。**

**結果、必須 21 本のうち 3 本が確実に赤くなる状態で push した** ——
`verify-generated` が落ちて 3 platform の `ci-native` が、
そして**自分がその直前に足したばかりの検査**が落ちて速いレーンが。

**既存の門はどれも止めなかった:**

- `block-bulk-git-add.sh` は `-A` と `.` を止めるが **`-u` は素通しする**
  （コメントは「生成物、一時的なデバッグ変更を巻き込む」と書いているのに、
  実装がその 2 つを拾う経路を塞いでいない —— **理由と実装がずれていた**）
- `check-generated-file-edit.sh` は Write/Edit の直後に指摘するが、
  **hook の外で書き換えたもの**（`sed` で注入した行）は見ない
- `dev.ps1 test` は落ちる —— **ただし push する前に誰も走らせなかった**

**`-u` だけを塞ぐ手は採らなかった。** `git commit -a` が同じ形で残り、
**片方だけ塞ぐと塞がれていない動詞に移るだけ**である（このリポジトリは
同じ形を 2 度踏んでいる。必須チェックの穴）。**動詞ではなく結果を見る門**を
足した（`check-staged-generated-file.sh`）—— stage された生成物に注入の痕跡が
あれば `git commit` を止める。**対象を一覧で持たない**（生成物が先頭 5 行で
名乗る規約を見る）ので、生成物が増えても変わらない。

順序に 1 段足す:

```
1. 実装して、検査が通ることを確かめる
2. コミットする
3. 壊す → 落ちることを見る → git checkout -- で戻す
4. **戻ったことを確かめる**（git status が 3 の前と同じであること）
5. （必要なら）検査を直して 1 に戻る
```

**変異を当てる場所を分ける手もある。** レビュアーは
`git worktree add --detach <scratchpad> <sha>` で切り離した木を作り、
検査も変異もそちらで走らせて、終わったら `git worktree remove --force` した。
**本体への書き込みが 0 件になるので、混ざりようがない。**
他人がツリーを共有しているときは特に効く。

### 壊し方が空振りしていないか、置換の結果で確かめる

**「壊したのに落ちなかった」の前に、「本当に壊れたか」を見る。**

M4 で、改行コードの不一致（`\r\n` を期待したが working copy は LF）で
置換が空振りし、**「検査が効いていない」と誤って結論しかけた。** 置換した
はずのファイルは 1 バイトも変わっていなかった。

```powershell
$t = Get-Content $f -Raw
$n = $t -replace $pattern, ''
if ($n -eq $t) { Write-Host "!!! 置換が空振り" } else { Set-Content $f -Value $n -NoNewline }
```

**空振りは「検査が強い」と同じ見た目をする。** 区別できる形にしてから測る。

### 検査が届く場所と、番人が置かれている場所を突き合わせる

**手前に別の門があると、番人には一度も到達しない。**

M4 で `verify-android-page-size.ps1` に「PT_LOAD が 0 件なら落とす」番人を置き、
program header ごと 0 個の ELF で試した。**その入力は手前の「program header が
読めません」で落ちるので、番人には一度も届いていなかった** —— 番人を丸ごと
無効化しても検査は緑のままだった。header は 1 つ置き、種類だけ `PT_NOTE` に
することで初めて届いた。

**さらに、届いた後も終了コードだけでは区別が付かなかった。** 番人を外すと
StrictMode 下の `Measure-Object` が空入力で throw し、**やはり exit 1 になる。**
番人の値打ちは「読める形で落ちる」ことなので、**メッセージまで見る形**に
変えて初めて、番人の有無を検査が区別できるようになった。

**「落ちた」だけでは足りない場面がある** —— 落ちる理由が 2 つあるとき、
検査はその 2 つを区別できていない。

**M5 で 2 例目を踏んだ。** spec の `summary` に改行を禁じる `pattern` を
schema に足し、確かめるために**実物の JSON に生の改行を入れた。**
そのファイルは JSON として壊れているので、`System.Text.Json` が
パースの段で先に落とす —— **足した検査は 1 度も動いていなかった。**
逃がした改行（`"…\n…"`。JSON として妥当で、文字列の値だけに改行が入る）で
入れ直して初めて狙った門に届いた。

**入力が「本番が渡す形」かどうかを、手前の門ごと考えること。** 壊し方が
乱暴だと、番人ではなく門番が反応する。

### 述語のゆるさが、検査を静かに無力化する

M4 の 1 ブランチだけで 4 通り出た。**どれも「通るのに何も証明していない」形**である。

| 形 | 実例 | 直し方 |
| --- | --- | --- |
| **構造的に常に真** | 「5 platform のハッシュが全部違う」—— `Platform` 自体がハッシュに入るので、衝突は起こりようがない | 落ちうる命題に変える（「`Platform` を抜いたらハッシュが変わる」） |
| **部分一致** | `'…/libopencv_unity_native.a.meta'` が `…/libopencv_unity_native.a` を含むので、**binary の行を消しても通った** | 引用符ごと厳密に照合する |
| **大文字小文字** | PowerShell の `-match` は既定で区別しないので、`RequireTest` が `matrix.requireTest` に当たっていた | `-cmatch` と、具体的な形（`-RequireTest` か `RequireTest =`） |
| **散文に当たる** | `<# #>` の中の説明文に `(dll\|dylib\|so)` と書いてあり、コード側を直しても検査が落ちなかった | 行頭 `#` を落とすだけでは**ブロックコメントを除けない**。禁じたい**コードの形**（`-match '…'`）だけを狙う |
| **アンカーの意味を確かめていない**（M5） | 禁止文字の列挙は正しかったのに、`^[^\r\n<>&]+$` を `Regex.IsMatch` に掛けた結果が **`"末尾に改行。\n"` を通した** —— .NET の `$` は「文字列の末尾」だけでなく**「末尾の `\n` の直前」にも一致する**。`"…\r\n"` と `"…\n…"` は落ちるので、**禁じたはずのものの一部だけが通り抜けた** | 「一致したか」ではなく**「値の全体を覆ったか」**を見る（`var m = Regex.Match(v, p); m.Success && m.Length == v.Length`）。**pattern の綴りに賭けず、読む側で閉じる** |

**共通するのは「文字列が在るか」を見ていること。** 見たいのは
**その文字列がコードとして何をしているか**である。

**5 行目は少し違う形をしている。** 列挙も正規表現も正しく、**アンカーの意味だけが
思っていたものと違った。** しかも罠が二重だった: **ECMA-262 の `$`（`m` 無し）は
入力の末尾にしか一致しない**ので、`.NET` で書いたその検査は
**自分が読んでいる JSON schema の規定より弱かった** —— schema としては
弾かれる値を、実装が通していた。**「同じ正規表現」は「同じ言語の正規表現」ではない。**
自分が使う実装の**アンカーの定義**を読み、境界（末尾の改行、`\r\n`、中間の改行）を
1 つずつケースにすること。

### 検査が別の検査を壊していないか（並行実行）

M4 で、自分が書いたテストが**固定名の一時ファイル**を使い、`dev.ps1 test` が
tools のテストを他と並べて走らせたときに潰し合った —— 片方が消した直後に
もう片方が読みに行き、**無関係な assertion が落ちた。**

**「たまたま赤い」は「コードが理由で赤い」と区別できない。** 一時ファイルは
実行ごとに一意な名前にする。


### 自分でパースする検査は、本物の解釈を代理できない

**同じファイルを見ていても、読む主体が違えば別の検査である。**

M4 の最後の 1 件がこれだった。iOS の `.meta` に `iPhone:` と書いた ——
Unity 2019 以前の名前で、Unity 6 では `iOS:` である。

| 検査 | 何をした |
| --- | --- |
| `.meta` を**自分で YAML として読む**検査 | **通した。** `iPhone:` は YAML として正しい |
| **Unity に読ませて結果を問う**検査 | 落とした。`GetCompatibleWithPlatform(iOS)` が `false` |

**前者は後者の安い代理ではない。** 自分でパースする検査が見ているのは
「その文字列が在るか」で、本物が見ているのは「その文字列を自分が何と解釈するか」
である。**綴りの正しさ・キー名・列挙の値・schema にあるが実装が知らない項目**は、
全部この隙間に落ちる。

同じ形が CodeQL の設定にもある: `exclude` を `excludes` と綴り間違えても
**schema 検証は通り、CI は緑のまま**で、外したはずの指摘だけが黙って戻ってくる。

**片方しか無いなら、無い側が穴である。** 本物に問う検査が高い（Unity の起動が
要る等）としても、**安い側を「代わりに置いた」と記録しない。**

### 正本を写さない。正本から読む

**一覧を写した瞬間に、写した先は独立して古くなる。**

M4 で `VerifyOpenCvArtifact.Tests.ps1` がライセンスファイル名を **13 件直書き**
していた。検証器側は Android の分が増えて **15 件**になっており、
**テストが古い側を主張して、正しい実装のほうが落ちた。**

壊れ方が悪い: 落ちたのは Android とは無関係な desktop の必須レーンで、
**赤い場所と原因の場所が離れている。**

```powershell
# 検証器から読む。読めなければ落とす（黙って空にしない）
$src = Get-Content -LiteralPath $verifier -Raw
# ^ で行頭に固定する。固定しないとコメントの中の説明文に当たる
$m = [regex]::Match($src, '(?ms)^\$InertLicenseFiles\s*=\s*@\((.*?)^\)')
if (-not $m.Success) { throw "正本から一覧を読めませんでした。書き方が変わっています。" }
```

**「読めなければ落とす」まで書いて初めて成立する。** パースに失敗して空配列に
なると、**その検査は何も見なくなり、しかも通る。**

写して良いのは、**ずれたときに必ず赤くなる**場合だけである。ずれても
どちらかが黙って通るなら、それは 2 つの正本を持ったということである。

**そして「正本から読む」にも同じ条件が掛かる。** 上のライセンス名の読み取りが
今も正しいのは、**読んだ全件を通知文書と突き合わせる下流の検査がある**からで、
**取り落とすと落ちる**。**同じ書き方でも、読んだ値が検査対象にとって
必須でなければ、取り落としは観測できない。**

2026-09-02 に実際に踏んだ: 同じファイルで OpenCV の推移的依存の一覧を
正規表現で読む形にした。上の作法どおり `throw` も付け、コメントも剥がし、
複数行にも対応させた。**それでも取り落とし、テストは緑のままだった** ——
落とした module は合成ツリーに**在ってもよい**側で、無くても検証は通るからである。

**黙って壊れたのは「複数行 + 連結」の形である**（`@(...)` を複数行に割り、
その後ろに `+ @('c')` を足す）。**1 行で連結しただけなら上の `throw` に
掛かる** —— つまり**同じ「連結」でも、書き方によって throw する側と
黙る側に分かれる。** 「throw を付けたから安全」とは言えない。

**落ちない読み取りは、読んでいないのと同じである。**

**直し方は「もっと良いパーサ」ではなかった。** 検証スクリプトを読み直すと、
その一覧は必須ではなく許可の側だと分かった —— **つまり読む必要が無かった。**
一覧を読むのをやめ、「許可されるか」という**結果**を 1 つ名指しで見る形にした
（許可リストから外すと実際に落ちる）。

**読む前に問う: 読んだ値を取り落としたら、この検査は落ちるか。**
落ちないなら、読むのをやめて**結果**を見る道を探す。


### 無音の待ちは、遅さと区別が付かない

**進捗を出さない step は、進んでいるのか止まっているのかを区別できない。**

M4 で macOS に Unity を入れようとして **64 分待って打ち切った。** 「Editor は
数 GB あるから」と考え、次は 25 分の上限を置いて**進捗を出すようにした。**
すると 1 行目で正体が出た:

```
[hub] ? Please select preferred architecture:
[hub] ❯ Apple silicon
[hub]   Intel
```

**遅いのではなく、対話プロンプトで止まっていた。** `--headless` を渡しても
Hub は聞いてくる。最初の 1 分で止まっており、残りの 63 分は何もしていない。

**CI で対話を待つのは、いつまでも終わらないのと同じである。** 外部コマンドを
CI から呼ぶときは:

- **進捗を出す。** 無音のまま長い step を作らない
- **step 単位の `timeout-minutes` を置く。** job 全体の上限しか無いと、
  1 つの step が全部を食い潰しても気づけない
- **stdin を閉じる**（`< /dev/null`）。プロンプトが出たら待たずに落ちる

**「大きいから遅いのだろう」は仮説であって観測ではない。** 観測を出す仕掛けを
先に置けば、64 分は 1 分で済んだ。

### 壊し方が、検査の外側でプロセスごと殺していないか

**`CLAUDE.md` は「クラッシュは赤いテストでなければならない」と定めている。
これが成立するのはレーンによる。**

M5 で、生成した到達性テストに `ocvu_debug_crash` を含めてよいかを確かめようと、
Unity 経由でそれを呼んだ。**テストは赤くならなかった** ——
**レーンが 10 分以上返らず、結果 XML が 1 バイトも出ない。**

| レーン | `ocvu_debug_crash` を呼ぶと |
| --- | --- |
| L3（`dev.ps1 test-managed-probe`） | **赤くなる。** `AccessViolationException` で 6 秒後に非 0 終了、hang は 36 秒で `--blame-hang` に捕まる |
| Unity（EditMode / Player） | **無音で固まる。** 判定を書き出す主体（Unity）ごと死ぬので、書かれるはずの結果が存在しない |

**判定を書き出す主体が死ぬ壊し方は、赤ではなく無である。** テストランナーが
別プロセスを監視している層（L3）と、ランナー自身が壊れる層（Unity）は別物で、
**前者で成立した「クラッシュ耐性」を後者にそのまま持ち込めない。**

だから到達性テストはこの 1 本だけを呼ばない（`bindings/spec/infra.json` の
`reachableNote`）。**「外した」ことを spec に理由つきで書かせているのは、
次の人が同じことを 10 分かけて確かめ直さないためである。**

### 列挙に基づく門を、出口側の構造に基づく門へ変える

**禁止文字の集合は、必ず「著者が思いついた範囲」である。**
M5 で spec に `\r` `\n` `<` `>` `&` `*/` を禁じたが、これは
**壊れた生成物を 3 つ見てから足した一覧**であって、網羅ではない。

**出口側で構造を見れば、どの文字が原因かに依存しない。**
`docs/api-map.md` については、**出来上がった Markdown を読み直して**
「各行の区切りが見出しと同じ個数」「本体の行数が spec の entry 数と一致」を
生成の直後に見る形にした —— 改行でも、逃がし損ねた `|` でも、
**行が割れれば列数か行数が変わるので落ちる。**

2 つ注意がある。**(a) 中間のデータではなく出来上がった文字列を読むこと** ——
組み立てた側と同じ数え方をすると、両方が同じ間違いをしたときに素通りする。
**(b) 数え方を対象の規則に合わせること** —— 1 波目に書いた `(?<!\\)\|` は
「直前が `\` なら区切りではない」と読む形で、**`\` を逃がし損ねた欠陥を
そのまま見逃した**（Markdown では `\\|` の `|` は区切りである）。

**ただし配分を考えること。同じ検査をどの出口にも足すのは無駄である。**

| 出口 | 下流に検査が在るか | 足す価値 |
| --- | --- | --- |
| C ヘッダ | **コンパイラが持つ。** 壊れれば L1 のビルドが落ちる（実測で C2143） | **薄い。** 手書きの構造検査はコンパイラより弱い |
| C# の XML doc | `GenerateDocumentationFile` を有効にすればコンパイラが引き継ぐ | 有効化のほうが本筋。**いまは有効ではない** |
| Markdown（API 対応表） | **無い。Markdown は決して文句を言わない** | **ここに足すのが最適だった** |

**「下流に検査が 1 つも無い出口」を先に探すこと。** 列挙を増やすより、
そこに構造の門を 1 つ置くほうが効く。

### 4. 終了コードを見る。出力を数えない

`grep -c PASS` は検査ではない。失敗した実行にも PASS 行は出る。

M1 では実際に、`test-tools-slow` を「27 PASS 緑」と報告した直後に、その実行が
exit 1 だったことが分かった。PASS 行を数えて終了コードを見ていなかった。

パイプを通すと `$?` はパイプ最後のコマンドの値になる。`| tail -3` を付けたまま
`echo $?` すると `tail` の終了コードを読むことになる。

```
cmd > /tmp/out.txt 2>&1; echo $?    # これは cmd の終了コード
cmd | tail -3; echo $?              # これは tail の終了コード
```

### 5. その検査が実際に走る場所を確かめる

**どのレーンからも走らないテストは、検証機構ではない。**

`CLAUDE.md` は「CI が唯一の正本の検証結果」と定めている。人が思い出したときだけ
走るものは、その基準を満たさない。

書いたら `tools/dev.ps1` の該当サブコマンドか、`.github/workflows/` のどこかに
実際に配線されていることを `grep` で確認する。コメントに「CI 側の担当」と書くのは
配線ではない。M1 ではまさにこれが起きた — comment がその分担を宣言していたが、
どの workflow もそのファイルを呼んでいなかった。

秒単位のローカルループに乗らない重い検査は `test-tools-slow` に置き、CI で走らせる。
どちらにも置かない、という選択肢は無い。

**どこからも走らない検査は、静かに腐る。** M4 の最後にこれを実測した ——
`dev.ps1 test-unity-tarball`（全部入り tarball の導入検証）はどの workflow
からも走っておらず、**モバイルを足した時点から壊れていた。** 期待する binary
の数が `3` と直書きされ、binary の判定が `(dll|dylib|so)` の列挙だったので、
5 platform になったとたん **iOS の `.a` を binary と認めず、数も合わなくなった。**
**同じ 2 つの欠陥は packer 側では直っていた** —— 走る側だけが直り、走らない側は
そのまま残った。

気づいたのは、無関係な作業の途中で 1 度手で回したからである。**それが無ければ
次のリリースまで誰も知らなかった。**

### 6. 一段先が空いていないか見る

検査が落ちたとき、**何をすれば緑に戻るか**を考える。その操作だけで戻せてしまい、
本来直すべきものが直らないなら、そこが次の穴である。

F5 がこれだった。新しい license ファイル → verify が落ちる → 一覧に名前を足す →
緑に戻る。利用者が読む文書は放置されたままで、何も赤くならない。

### 契約を書いただけで、実装がそれを満たすかは誰も見ていない

**`bindings/spec/*.json` の `summary` は契約である** —— C の doc コメント・C# の
XML doc・`docs/api-map.md` の 3 箇所に同時に出る。しかし `verify-generated` が見るのは
**生成物が spec と一致するか**だけで、**spec が書いた挙動を実装がするかは見ていない。**

M5 の module 追加で 2 回踏んだ:

- `summary` が「符号化できない長さの text は `OCVU_STATUS_OPENCV_ERROR` になる」と
  約束していたが、実装は `cv::Exception` を個別に受けておらず `UNKNOWN_ERROR` を返していた。
  **ビルドも L1 も L3 も緑のまま。** レビュアーが DLL に 5000 バイトの文字列を
  P/Invoke して初めて分かった
- 実装が `summary` に無い前処理（画像の拡大と余白の付加）をしていた。**こちらは逆向き**
  —— 実装がしていることを契約が書いていない

**約束したなら、その約束を実証するテストを書く。** 上の 1 件目は
`EncodeReportsAnOpenCvErrorForTextThatDoesNotFit` を足して閉じた（catch を入れる前に
赤くなることを見てから入れた）。

**公開 API の doc も同じ**である。生成された XML doc は `internal` の宣言に付くので
**利用者からは見えない** —— `Runtime/Core` の公開クラスに書いた doc だけが読まれる。
M5 では `CvQrCode.Encode` が `dst` を丸ごと差し替えることが公開 doc に無く、
同じリポジトリの `CvCodecs.Decode` は明記していた。**書き分けが不統一なら、
どちらかが嘘である。**

### 合計だけを固定した検査は、中身の入れ替えを通す

境界に出す struct の layout を `sizeof == 28` と `Marshal.SizeOf == 28` の両側で
固定しても、**同じ型のフィールドを入れ替えると両方通る**（`float x, y` を
`float y, x` にしても 28 バイトのままである）。M5 の `ocvu_keypoint` がこの形だった。

**`Marshal.OffsetOf` を全フィールド分並べる**と閉じる。壊れ方は「呼んだ場所ではなく、
後から値を読む無関係な場所」型なので、合計だけでは足りない。

### ディレクトリが在ることは、中身が在ることではない

M5 の作業中、`test-tools-slow` を中断した結果 **OpenCV のツリーが空になった**。
実装者は「無傷を確認済み」と報告したが、**親ディレクトリの存在だけを見ていた。**
`tools/opencv.ps1 status` も `state: present` と答える —— **空のディレクトリを
present と判定する**ためである。

**「確認した」と「確認できていた」は別。** 中身を数えること（`ls | grep -c`）。

### 恒等な設定で確かめると、正しい実装と退化実装が同じ出力を出す

M5 の `calib` で、「同じ handle を src と dst に渡してもよい」という契約を
**画素単位で 256 個比較するテスト**を足した。それでも
`if (src == dst) { return OCVU_STATUS_OK; }` という**何もしない実装**を入れて
全件が緑のままだった。

原因は、比較を足すのと同時に**歪み係数を 0 にした**ことである。係数が 0 なら
補正は恒等写像なので、**正しい実装の出力と「何もしない」実装の出力が一致する。**
「ただの複製」でも通る。足した 256 個の比較が固定していたのは、
すぐ隣の既存テストが既に固定していた事実と同じものだった。

**assertion の数は証拠ではない。** 見るのは「その設定で、正しい実装と壊れた実装が
違う値を出すか」だけである。パラメータを穏当な側に寄せると、たいてい両者は一致する。

**同じ形が、対称性でも起きる。** 「x と y が交互に並ぶ」ことを確かめるテストを
7x7 の**正方形**の盤で書くと、x と y を入れ替えても行と列の範囲が同じなので
何も落ちない。7x6 にした瞬間に落ちるようになった。**確かめたい非対称性が
入力の対称性に隠れていないか**を見る。

**そして最も大事なこと: この節の指摘に対する「修正」自体が、同じ穴を持ちうる。**
上の 2 つはどちらも、「テストが狙った性質を見ていない」という指摘を受けて
書き直した**後**の状態で見つかった。**壊して落ちることを見る手順は、修正の側にも
同じだけ当てる。**


### 同じ作業ツリーで 2 人が同時に壊すと、両方向に嘘が出る

M5 の `calib` で、実装者と再レビュアーが同時に同じソースへ変異を当てていた。

**壊れ方が両方向で、しかも無音である**:

- 一方が変異を入れた直後にもう一方が `git checkout --` すると、ビルドは健全な
  コードになり、**「壊しても緑 → 検査が効いていない」という誤った判定**が出る
- 逆向きなら、変異を消された側が「壊しても緑」を見て**要らない直しを入れる**

`CLAUDE.md` が `dev.ps1` のレーンについて言っている相互排他は、**変異を当てる作業にも
同じだけ掛かる。** 壊す前に、そのツリーを触るのが自分だけであることを確かめる
（`git status` が clean であることと、ビルドが動いていないことの両方を見る）。

**誰の変異が入った状態で測ったのか確定していない観測は、証拠として使えない。**
たとえ期待どおりの結果が出ていても、取り直す。


## やってはいけないこと

- 通ったことを、検査していることの証拠として報告する
- 推測した入力形式に対して assertion を書く（実物を見ずに）
- 壊して落ちることを確認せずに「テストを追加した」と報告する
- 出力の PASS 行を数えて緑と判断する
- 検査を書いたが、どこからも呼ばれていない状態で完了とする
- 列挙を 1 つ足して「同種の問題を塞いだ」とする
- 既にある緑のレーンを、壊して反応を見ないまま完了条件の証拠にする
- 壊れていても同じ値を返す述語（常に true を返す能力照会など）で assertion を書く
- SKIP を合格として数える
