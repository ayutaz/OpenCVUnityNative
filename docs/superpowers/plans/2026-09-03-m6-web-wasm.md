# M6 — Web / Wasm 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Unity Web Player 上で、**他の platform と同じ検証本体が通る**状態を、**Unity 同梱 Emscripten と整合した形**で作る。具体的には spec のゴールの 3 つ —— (1) `tests/UnityProject/Assets/Tests/Shared/` の検証本体が Web Player で通る（**写して 3 つ目を作らない**）、(2) `AbiReachabilityChecks.g.cs` が spec の載せる宣言を Web でも 1 本残らず呼べる（**stripping が消せるのは呼ばれない宣言なので、確かめられるのは Player だけである**）、(3) 全部入りの package に WebGL が入り、**Unity が Web の物だけを有効にする**。

**Architecture:** Web は **6 つ目の platform** であり、**クロスビルド**かつ**静的ライブラリ**である —— iOS と同じ 2 つの性質を同時に持つ。したがって `cmake/toolchains/web-wasm.cmake` を新設し、OpenCV のアーカイブは自分で束ね、P/Invoke は `DllImport("__Internal")` になる。**iOS で通った道の 9 割はそのまま使える。**

**Tech Stack:** Emscripten 3.1.39（Unity 6000.3.16f1 同梱）／CMake + Ninja／OpenCV 5.0.0／Unity 6000.3.16f1 WebGL Player／headless browser（Playwright）

**Spec:** `docs/roadmap.md` の「M6 — Web / Wasm」節（目的・ゴール・完了条件・非ゴール）。**この計画は 5 つの完了条件を Task に割り当てたものである**（**5 つ目「配れる」は 2026-09-03 に足した** —— M4 で「ビルドできる／配れる／動く」は別物だと決めたのに、Web だけ「配れる」の条件が無かった）。

**完了条件と Task の対応**（**Task の番号順は依存関係順であって、条件の番号順ではない**）:

| spec の完了条件 | Task |
| --- | --- |
| 1. Emscripten の版の対応表と、CI での不一致検出 | **Task 1** |
| 2. Wasm object を生成し `.a` にまとめる（**まとめたことを実証する**） | **Task 2**（OpenCV 側）+ **Task 3**（plugin 側と束ね） |
| 3. single-thread / SIMD（**flag を外すと落ちる**ところまで） | **Task 5** |
| 4. 全部入りに WebGL が入り、gating が Web の物だけを有効にする | **Task 4** |
| 5. browser E2E（**0 件で緑にしない**） | **Task 6** |
| （条件ではない。完了の判定と文書） | **Task 7** |

**この表は spec と計画がずれたときに最初に嘘になる場所である。** 条件を足したら行を足すこと。

**この計画の価値について、spec の訂正を引き継ぐ。** roadmap の M6 節は長らく「競合が持たない Web 対応」と書いていたが**誤りで**、**Enox の OpenCV for Unity は WebGL に対応している**（2026-09-03 に訂正）。**Web は有償の競合に対する差別化ではない。** 実装や PR 本文で「競合が持たない」と書かないこと。

## Global Constraints

`CLAUDE.md` の不変条件がすべて掛かる。**この計画で特に効くものだけ**を再掲する。

- **C ABI が唯一の native contract。** `cv::Mat*` や STL 型を境界の外へ出さない。
- **例外を ABI の外へ伝播させない。** 公開 ABI 関数は `OCVU_TRY_BEGIN` / `OCVU_TRY_END` で囲む（囲まない 4 本の例外は `native/src/ocvu_error.h` の隣にある）。
- **境界の宣言を手で書かない。** `bindings/spec/*.json` が正本で、`./tools/dev.ps1 generate` が C ヘッダ・C# の P/Invoke・到達性テスト・API 対応表を書き出す。**`dev.ps1 verify-generated` が食い違いを落とす。**
- **`OCVU_ABI_VERSION` は 1 のままである。** **この計画で ABI 関数を 1 本も足さない**（platform を足すのであって API を足すのではない）。増やしたくなったら、それは別の計画である。
- **CI はローカルと同一のコマンド（`tools/dev.ps1`）を呼ぶ。** CI 専用の手順を作らない。全 job に `timeout-minutes` を設定する。
- **検査を足す・変えるときは `prove-a-check-works` skill に従う。** 壊して落ちることを見るまで、その検査は動くと言えない。**1 通りで確かめて満足しない。**
- **`dev.ps1` のレーンは相互排他である。** 2 つ同時に走らせない。
- **非 ASCII を出力する PowerShell スクリプトは `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()` を先頭に置く。**
- **PR の前に、差分を書いていない別のエージェントがレビューする**（`CLAUDE.md` の「変更を main へ入れるまで」）。

| 同梱物 | `llvm/`（`clang.exe` / `llvm-ar.exe`）・`binaryen/`・`node/`（**v12.18.1**）・`python/`・`emscripten/` | ディレクトリ一覧 |

### **platform を足しても、既存 5 つの OpenCV は作り直しにならない**（実測）

**`calib` を足したときは `Modules` を触ったので構成ハッシュが全 platform で動き、5 platform 分を作り直した**（`4785d98e9aad` → `09fcbe260d87`）。**今回は違う。**

`Get-OpenCvConfig` が組み立てるのは `Platform / Tag / Modules / Toolchain / CMakeArgs` で、`Toolchain` は `Toolchains[$Platform]`、`CMakeArgs` は共通 + `PlatformCMakeArgs[$Platform]` である。**`Toolchains` に新しいキーを足しても、既存 platform の側は 1 バイトも変わらない。**

**測った**（`Toolchains` に `web-wasm` を足した psd1 を別ディレクトリに置き、両方でハッシュを算出）:

| platform | 現在 | `web-wasm` を足した後 |
| --- | --- | --- |
| windows-x64 | `09fcbe260d87` | **`09fcbe260d87`** |
| linux-x64 | `3a66080c1b3a` | **`3a66080c1b3a`** |
| android-arm64 | `95bad3e2426a` | **`95bad3e2426a`** |

**ビルドされるのは `web-wasm` の 1 つだけである。** ただし **`Modules` を触ったらこの前提は消える** —— Web のために module を足したくなったら、その瞬間に 6 platform 分の作り直しになる。**この計画では `Modules` を触らない**（`core imgproc imgcodecs objdetect features calib` のまま）。

### `add-a-platform` skill を先に読むこと

**一覧を持つ場所は 17 箇所ある。** 語彙が違うので grep 1 回では揃わない。**M4 では、クロスビルドが緑になってから CI で 8 回落ちた。** その 8 回の内訳と、踏んだ順の罠が skill にある。**特に次の 3 つは、この計画でそのまま再来する:**

1. **`.meta` の platform キーは、Unity が知らない名前だと黙って無効になる**（iOS で `iPhone:` と書いて踏んだ。**自分でパースする検査は通り、Unity に問う検査だけが落とした**）
2. **静的ライブラリを配るなら、依存アーカイブは自分で束ねる**（CMake は STATIC に依存を取り込まない。**ビルドは成功し、リンクの段で壊れる**）
3. **クロスでは `find_package` が sysroot に閉じ込められる**

## Task 1: Emscripten を駆動できるようにし、版の不一致を CI が捕まえる

**完了条件 1**（Unity version と Emscripten version の対応表を作り、CI で不一致を検出する）を閉じる。

**Interfaces:**
- Produces: `Get-EmscriptenToolchain`（`tools/Emscripten.psm1`）—— `[hashtable]` を返す（`Root` / `EmCC` / `EmAr` / `Version` / `CMakeToolchainFile` / `Source`（`'unity'` か `'emsdk'`））。Task 2 以降がこれを使う。
- Produces: `tools/emscripten-versions.psd1` —— `@{ '6000.3' = @{ Emscripten = '3.1.39'; Commit = 'a2ee372…' } }`。

### なぜ対応表が要るか

**CI に Unity は無い**（`build-opencv` も `ci-native` も Unity を起動しない）。したがって CI は **emsdk から Emscripten を入れる**ことになる。**そこで入れる版が、Unity が実際に同梱する版と食い違うと、ローカルで動く wasm が Unity のビルドで壊れる。**

**「対応表を作る」だけでは不十分である** —— 表は写しなので、Unity を上げた日に静かに古くなる。**だから 2 つの検査を対にする:**

| 検査 | どこで走るか | 何を見るか | Unity が要るか |
| --- | --- | --- | --- |
| A | 速いレーン（`dev.ps1 test`） | `ProjectVersion.txt` の Unity 版が表に在り、**workflow が pin している emsdk の版が表と一致する** | **要らない** |
| B | `ci-unity`（Unity が在る） | **Unity が実際に同梱する `emscripten-version.txt` が表と一致する** | 要る |

**A だけでは「表が現実と合っているか」を誰も見ない。B だけでは Unity レーンが動くまで気づけない。**

**Interfaces:**

- Produces: `third_party/opencv/<web-wasm のハッシュ>/` に `lib*.a` が入った木。`opencv.ps1 verify` が通る。

- [ ] **Step 1: `web-wasm` を受理しないことを確かめる（RED）**

```
pwsh -NoProfile -File tools/opencv.ps1 status -Platform web-wasm
```

期待: **`ValidateSet` で弾かれる。** これが RED である。

- [ ] **Step 2: 構成に `web-wasm` を足す**

`tools/opencv-config.psd1` の `Toolchains` と `PlatformCMakeArgs` に足す。**`Modules` は触らない**（触ると 6 platform 分の作り直しになる。上の実測を参照）。

`PlatformCMakeArgs['web-wasm']` に最低限入るもの:

```
-DBUILD_SHARED_LIBS=OFF          # wasm に共有ライブラリは無い
-DWITH_PTHREADS_PF=OFF           # single-thread を先に成立させる（完了条件 3）
```

**この一覧は仮説である。** 次の step で実際に configure して、**summary が想定外の依存を有効にしていないか**を見る（`CLAUDE.md`: 「CMake configure summary を保存し、想定外の依存が有効なら CI を失敗させる」）。

## Task 3: plugin を静的ライブラリとしてクロスビルドし、OpenCV を束ねる

**完了条件 2 の後半。iOS で踏んだ罠が、そのまま再来する。**

```

```

期待: **`find_package(OpenCV)` が見つからない**で落ちる —— クロスでは探索が sysroot に閉じ込められる（罠 3）。**これが RED である。**

- [ ] **Step 2: 探索の根を足し、package の探索だけ緩める**

`cmake/FindOpenCvUnityDeps.cmake` で `CMAKE_FIND_ROOT_PATH` にこちらの木を足し、**`CMAKE_FIND_ROOT_PATH_MODE_PACKAGE` だけ** `BOTH` にする。**library / include まで緩めない** —— host の `.a` やヘッダを拾う経路が開く。

- [ ] **Step 3: ビルドが通ることを確かめる**

```
pwsh -NoProfile -Command "./tools/dev.ps1 build -Platform web-wasm"
```

期待: exit 0。**`.a` ができる。**

- [ ] **Step 4: 「束ねられていない」ことを先に実証する（ここが最も重要）**

**CMake は STATIC ライブラリに依存アーカイブを取り込まない。** 出来た `.a` は自分の object しか含まず、`cv::` は未解決のまま残る。**ビルドは成功する。**

**iOS ではこれを 2 つの検査で見ようとして、2 つとも空振りしていた**（`ar t` は OpenCV ではなく自分の object に当たり、`nm -u | match 'cv::'` は nm が demangle しないので決して真にならない）。**同じ間違いをしない。**

見るのは「**こちらの object が要求する `cv::` のシンボルを、この archive 自身が定義しているか**」である。**mangle された名前で見る**（`llvm-nm` は同梱の `llvm/` に在る）:

```bash
NM="<Emscripten root>/llvm/llvm-nm.exe"
A="Packages/.../Runtime/Plugins/WebGL/libopencv_unity_native.a"
# 未定義のうち、OpenCV 由来（_ZN2cv…）のもの
"$NM" --undefined-only "$A" | grep -c '_ZN2cv'
# 定義済みのうち、同じもの
"$NM" --defined-only  "$A" | grep -c '_ZN2cv'
```

**束ねる前**: 未定義が 1 以上、定義済みが 0。**これを記録する。**

- [ ] **Step 5: `emar` で束ね、負の対照が落ちることを見る**

`native/CMakeLists.txt` に、`emar` で OpenCV のアーカイブを展開して自分の object と一緒に固め直す step を足す（iOS の `libtool` に相当）。

**そして検査を書く。** `tools/verify-static-bundle.ps1`（iOS と共通化できるならする）:

- 未定義の `_ZN2cv` が **0 件**であること
- 定義済みの `_ZN2cv` が **1 件以上**であること

**両方を見る。** 前者だけだと「空の archive」が通り、後者だけだと「束ねたが自分の object が入っていない」が通る。

**負の対照**: 束ねる前の `.a`（Step 4 で測ったもの）を検査に食わせて**落ちること**を見る。**同じ step の中で毎回それを裏づける形にする**（M4 の iOS がそうしている）。

- [ ] **Step 6: `ci-native.yml` にクロスビルド job を足す**

**L1 は走らない**（クロスした GoogleTest を host で実行できない）。**ビルドと束ね検査だけの job である**ことを job 名に書く（`Web wasm32 (cross-build)`）。

- [ ] **Step 7: コミット**


## この計画が意図的に決めていること

| 決めたこと | 理由 |
| --- | --- |
| **`Modules` を触らない** | 触ると構成ハッシュが全 platform で動き、**6 platform 分の OpenCV を作り直す**（`calib` で実測）。Web のために module を足したくなったら、それは別の計画である |
| **`-asan` の preset を作らない** | クロスした sanitizer を host で走らせられない。モバイル 2 つと同じ扱い |
| **ABI 関数を 1 本も足さない** | platform を足すのであって API を足すのではない。`OCVU_ABI_VERSION` は 1 のまま |
| **emsdk を CI の経路にする** | CI に Unity は無い。**その代わり、版が Unity と食い違わないことを Task 1 の 2 つの検査が対で見る** |
| **threads profile をやらない** | roadmap の非ゴール。single-thread / SIMD を先に成立させる |
| **配布を含めない** | 2026-09-03 の決定で、配るのは M6 の後 |
| **`dnn` を触らない** | M7 の担当。**OpenCV 5.0 で作り込むと 5.1 で作り直しになる**根拠が roadmap の M7 節にある。`Modules` を触らないという上の決定とも一致する |

## この計画が決めていないこと（着手して測ってから決める）

- **OpenCV の wasm 向け CMake flag の最終形。** Task 2 Step 2 の一覧は仮説であり、**configure summary を読んでから確定する。**
- **`emar` で束ねる正確な手順。** iOS の `libtool` に相当するが、**同じにはならない。** Task 3 Step 4 で「束ねられていない」ことを先に測り、それが 0 になる形を探す。

## 予想される CI 往復

**M4 では、クロスビルドが緑になってから CI で 8 回落ちた。** Web も同じ性質（**手元に無い OS・無い SDK・無い Unity がやることを、手元では試せない**）を持つので、**同じ規模の往復を見込むこと。**

減らす方法は 3 つだけである:

1. **1 コミット 1 原因にする**（まとめて直すと、どれが効いたか分からない）
2. **仮説のまま直さない**（M4 の最後の 1 件は、仮説が反証されて原因は別だった）
3. **落ちた job のログを、要約ではなく本文で読む**（M4 の 8 件中 5 件は、エラーの 1 行下に原因が書いてあった）
